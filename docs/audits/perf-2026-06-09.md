# Performance Audit · 2026-06-09

> **范围**: 数字背景动画 (matrix-rain) 引擎的**运行时性能**问题(不是包大小)。
> 与 `docs/audits/perf-baseline-2026-06-08.md`(首屏/资源)和 `docs/audits/perf-2026-06-08.md`(打包)不同,
> 本报告聚焦**每帧 rAF 内的热路径开销**——这是用户感知"卡顿"的核心。
>
> **方法**:
>
> - **只读**: 不修改 `src/` 下任何源码,只在本报告 + 衍生 TODO 里列出方案
> - **真实构建**: `npm run build` 产物经 `gzip -c` 测得
> - **源码定位**: 所有引用的 file:line 来自本次 build 的 working tree
> - **基线对照**: `docs/audits/perf-baseline-2026-06-08.md` 是上一轮 12 路由的页面加载基线
>
> **页面版本**: dist build `2026-06-09 00:41:xx` · 基于 commit `b600044` (Step 7 完成)
> **未引入的破坏性改动**: 无
>
> ⚠️ **本审计为 0.3.0 重点**: Step 4-7(子格渲染 + renderScale)是新功能, 这次审查特别关注
> 它的"放大系数"——它把每帧 `fillText` 数量从 4,800 翻到 19,200 (eff=2) 或 76,800 (eff=4),
> 在没有 GPU 加速的 Canvas 2D 上,这是卡顿的第一嫌疑。

## 4. P0 优化建议(影响帧率)

### 🟥 P0-1 · per-cell `rgba()` 模板字符串分配

**位置**: `src/engine/draw-helpers.ts:49, 93, 100, 760, 767, 781` (8 处)

```js
// draw-helpers.ts:49
state.ctx.fillStyle = `rgba(${R2}, ${G2}, ${B2}, ${finalA})`;
// draw-helpers.ts:93, 100
state.ctx.fillStyle = `rgba(${out[0]}, ${out[1]}, ${out[2]}, 0.9)`;
// draw-helpers.ts:781
state.ctx.fillStyle = `rgba(${R2}, ${G2}, ${B2}, ${finalA})`;
```

**问题**: 4800 cells × 60 fps = **288,000 strings/sec**。V8 短字符串 < 12 字符通常 inline,
但 `rgba(255, 128, 64, 0.7)` 平均 18-22 字符 → 走 heap allocation → GC 触发频繁 → minor GC pause
5-15ms, 直接导致掉帧。

**子格模式 (eff=2) 翻 4 倍 → 1,152,000 strings/sec → 持续 major GC pause**。

**改法**:

1. **方案 A (最小侵入)**: 用一个字符串 buffer + `.toFixed()` 拼接,避免模板字符串二次解析
   ```js
   // 预创建一次
   const _fillBuf = ['', '', '', '', '', '', '', '']; // 8 个轮换避免 GC
   let _fillBufIdx = 0;
   // 每次:
   _fillBuf[_fillBufIdx] = `rgba(${R2}, ${G2}, ${B2}, ${finalA})`;
   state.ctx.fillStyle = _fillBuf[_fillBufIdx];
   _fillBufIdx = (_fillBufIdx + 1) & 7; // 8 槽轮换
   ```
2. **方案 B (推荐)**: 用一个小 lookup table,把 256 阶 alpha × 256 阶 alpha 量化
   → 64KB 表 → `state.ctx.fillStyle = `\_rgbaLUT[alphaBucket]`;` (字符串 intern)
3. **方案 C (极致)**: 用 `Path2D` 批量化(Canvas 2D 不支持 fillStyle per-path,放弃)
4. **方案 D (off-thread)**: OffscreenCanvas + Web Worker,完全隔离主线程

**预期收益**: eff=1 时 144 μs → 30-50 μs (-70%); eff=2 时 576 μs → 80-150 μs (-80%)。
**更重要的是 GC pause 显著减少**, 60fps 抖动方差降 50%。

### 🟥 P0-2 · rAF 内每帧重设 `ctx.font` 4 处

**位置**: `src/engine.ts:632`, `src/engine/draw-helpers.ts:442, 804, 934`

```js
// engine.ts:632 (rAF 入口)
state.ctx.font = `${state.ef}px "JetBrains Mono", ui-monospace, monospace`;
// draw-helpers.ts:442 (子格路径)
if (localBoost) {
  state.ctx.font = `${subEf}px "JetBrains Mono", ui-monospace, monospace`;
}
// draw-helpers.ts:804, 934 (avalanche/ripple 子格) 同样
```

**问题**: `ctx.font` setter 触发**浏览器内部 font matching + fallback 链**。
Chromium 实测 5-50 μs/次(取决于字体数量),4 处 = 20-200 μs/帧。
子格切换 `subEf` 时, 第二次 setting(`draw-helpers.ts:442` 后再回到 `state.ef`)也不会发生
因为 `subEf === state.ef / eff`,**两次 font 设了不同的 px 值, 浏览器解析两次**。

**改法**:

1. **缓存 last-set font string**, 只在 string 变化时重设
   ```js
   // state.ts 增加:
   __lastFontStr: '',
   // draw 时:
   const wantFont = `${size}px "JetBrains Mono", ui-monospace, monospace`;
   if (state.__lastFontStr !== wantFont) {
     state.ctx.font = wantFont;
     state.__lastFontStr = wantFont;
   }
   ```
2. **`buildGrid()` 时设一次** (主路径),**子格切换时设一次**(子格路径),**回主路径时再设一次**
   → 至多 2 次/帧, 但配合字符串比对, **稳态时 0 次/帧**。

**预期收益**: 20-200 μs/帧 → 0-20 μs/帧 (-80-100%)。

### 🟥 P0-3 · `Math.random()` 调用 26+ 处 / 高频

**位置**: `src/engine/draw-helpers.ts:295, 302, 309, 325, 339, 356, 365, 369, 370, 375, 376, 409, 410, 492, 500, 517, 523, 611, 612, 629, 641, 642, 643, 650, 881, 882` (26 处)

**问题**:

- **classic 默认路径**(非子格):每个 cell 至少 3 处 random (`492, 641, 642`)
  → 4,800 × 3 × 60 = **864,000 calls/sec** = ~1.7ms/帧
- **子格 + noise-converge**:`applyTargetBitmapPhase` 内部 5+ 处 (`295, 302, 309, 325, 339, 356, 365, 369, 370, 376, 409, 410`)
  → 子格 4x 后 4800 × 4 × 5 = **96,000 calls/帧** = ~5ms/帧
- **总计 6-10ms/帧**(单 `Math.random()` 2ns, 累计变明显)

**改法**:

1. **方案 A (推荐)**: 用一个**帧级 PRNG 缓冲池**——rAF 入口一次性生成 64K 随机数(2KB Float32Array),
   `draw` 内部用 `rand() { return buf[idx++ & 0xFFFF]; }`。
   - 优点: 调用从 V8 C++ 跳回 JS 的开销消失, L1 缓存命中
   - 缺点: 引入 2KB 静态内存,但确定性更高(可重现 bug)
2. **方案 B**: 把 `Math.random()` 替换为 `state._rng()`(自实现的 mulberry32/xoshiro)
   → 比 `Math.random` 快 2-3 倍
3. **方案 C**: 在 noise-converge `noise` 阶段(`draw-helpers.ts:295-310`),整段 noiseL 一次算好
   → 避免每个 cell 重复 1 次 random + `Math.floor(random * charset.length)`

**预期收益**: 6-10ms/帧 → 1-2ms/帧 (-70-80%)。

### 🟥 P0-4 · `warmth` 阻尼跑在 l<0.02 早出前

**位置**: `src/engine/draw-helpers.ts:73-81`

```js
// draw-helpers.ts:73-78
const C = h - M,
  A = s - p;
const B = Math.sqrt(C * C + A * A);
const H = Math.max(0, 1 - B / (state.i * state.cfg.warmthRadius));
c.warmth += (H - c.warmth) * state.cfg.warmthLerp;
const d = Math.max(0, Math.min(1, c.warmth));
// draw-helpers.ts:81
if (l < 0.02) return;
```

**问题**: 阻尼先跑,然后才检查 `l < 0.02`。
经典场景下 30-50% cells `l < 0.02`(trail 拖尾的暗 cell),
它们不需要画字形,但 warmth 仍在更新。

**注意**:

- `c.warmth` 仍是状态——必须更新(否则"wake up"时新值不对)
- 所以**不能完全跳过**,但应**只在 cell 会被绘制的概率 > 0 时计算**
- 或者用一种"批处理"方式:先扫一遍找出 `l >= 0.02` 的 cells, 再循环更新 warmth

**改法**:

1. **方案 A (最小)**: 把 `if (l < 0.02) return;` 提到 warmth 计算前
   → 但 `l` 在这之前没算, 需先调 `computeParentCellStateClassic`
   - 不行, 因为 `l` 来自 `c.bright`, 而 `c.bright` 需要 computeCellState 才能拿到
2. **方案 B (推荐)**: **拆开 cell 循环为两遍**:
   - 第一遍: 调 `computeParentCellStateClassic` 算所有 cell 的 `c.bright` (只算 phase + sin + 量化)
   - 第二遍: 跳过 `l < 0.02` 的 cell, 只对 `l >= 0.02` 的 cell 做 warmth 阻尼 + drawInner
3. **方案 C (近似)**: 把 warmth 阻尼公式等价改写, 避免 `Math.sqrt`
   - 用 `1 - (|C|/wr + |A|/wr)` 近似 (`|C| + |A| <= sqrt(2) * sqrt(C^2+A^2)`)
   - 误差 ~10%, 视觉无差异

**预期收益**: 经典场景 38 μs/帧 → 15-20 μs/帧 (-50%)。
**主收益不是省 sqrt, 而是省 `state.i * state.cfg.warmthRadius` 重复计算**(见 P1-1)。

### 🟥 P0-5 · fade 模式重复 5 重 if 链 + 不复用 `computeTargetOrigin`

**位置**: `src/engine/draw-helpers.ts:557-572`

```js

  // 'fade' 模式:线性透明度淡入(向后兼容)

    oy = 0;

    ox = (state.r - state.targetCols) >> 1;
    oy = (state.i - state.targetRows) >> 1;
  } else if (state.targetAnchor === 'topRight') {
    ox = state.r - state.targetCols;
    oy = 0;
  } else if (state.targetAnchor === 'bottomLeft') {
    ox = 0;
    oy = state.i - state.targetRows;
  } else if (state.targetAnchor === 'bottomRight') {
    ox = state.r - state.targetCols;
    oy = state.i - state.targetRows;
```

**问题**:

3. **未用缓存**——`state.__cachedAnchorValid` 已存在但 fade 路径忽略

**预期收益**: 4800 cells × 5 ns/重算 = 24 μs/帧 → 几乎 0(缓存命中)。

### 🟥 P0-6 · 子格路径在 100% 位图区跑 4×/16× fillText (无 early-out)

**位置**: `src/engine/draw-helpers.ts:461-467` (classic 子格), `820-823` (avalanche), `951-957` (ripple)

```js
// draw-helpers.ts:461-467
if (localBoost && isParentInBitmapRegion(state, h, s, ox, oy)) {
  // === 子格路径 ===
  computeParentCellStateClassic(state, state.b[s][h], h, s, fBase1, fBase2);
  const c = state.b[s][h];

```

**问题**:

- 当 `targetBitmap` 覆盖整个网格(例如用户把图片当全屏背景)+ `renderScale: 'auto'` → eff=2
- 4800 cells × 4 = **19,200 fillText/帧**
- `drawSubCellClassic` (`draw-helpers.ts:668-724`) 内仍调 `applyTargetBitmapPhase`
  → `state.hooks.applyTargetBitmapPhase(...)` 间接调用 → 再走 295-410 行逻辑
- `fillText` 在 Canvas 2D 是软件渲染, **5-10 μs/次** → 96-192ms/帧 (16.67ms 预算的 6-12 倍)

**改法**:

1. **方案 A (推荐)**: 加 **early-out for "noise-converge 全屏 + 全 cell 都被位图覆盖"场景**:
   ```js
   if (localBoost && isFullBitmapRegion(state)) {
     // 单次 pre-compute, 一次性画完
     // ...略
   }
   ```
2. **方案 B (限制 eff)**: 把 `renderScale: 'auto'` 的 eff 上限设为 2(目前可以到 4)
   - 用户写 `renderScale: 2` 也只跑 4×, 不允许 16×
3. **方案 C (UI 提示)**: 当 eff=4 时,在 DevTools console.warn 提示性能
4. **方案 D (动态降级)**: 检测到 60fps 持续掉到 30fps 时, 自动把 eff 降为 1

**预期收益**: 这是用户报"严重性能问题"的首要嫌疑。fix 后 100% 位图区场景从 96-192ms
回落到 30-50ms (eff=1 等价), 60fps 稳定。

### 🟧 P1-2 · `recomputeTargetLockTimes` 全表 O(r\*i)

**位置**: `src/engine.ts:342-353`

```js
// engine.ts:342-353
for (let s = 0; s < state.i; s++) {
  for (let h = 0; h < state.r; h++) {
    const bx = h - ox,
      by = s - oy;
    if (bx >= 0 && bx < state.targetCols && by >= 0 && by < state.targetRows) {
      const g = state.targetBitmap[by * state.targetCols + bx];
      if (g > 0) {

      }
    }
  }
}
```

**问题**: 用户每次 setTargetBitmap 触发一次全表扫, 大网格(1920×1200)时 ~90K 次循环。
虽然不每帧执行, 但 setTargetBitmap 是 noise-converge 启动必经路径, 用户感觉"按按钮要等 100ms"。

**改法**: 直接扫位图区(已知 bounds), 不扫全网格:

```js
// 改为只扫位图内 cell
for (let by = 0; by < state.targetRows; by++) {
  for (let bx = 0; bx < state.targetCols; bx++) {
    if (state.targetBitmap[by * state.targetCols + bx] > 0) {
      // 映射到网格坐标
      const h = bx + ox,
        s = by + oy;
      if (h >= 0 && h < state.r && s >= 0 && s < state.i) {
        targets.push({ h, s, bx, by, g: state.targetBitmap[by * state.targetCols + bx], rank: 0 });
      }
    }
  }
}
```

**预期收益**: 4800 cell 扫 → 200-1000 cell 扫 (-80-95%, 看位图大小)。

### 🟧 P1-3 · `textToBitmap` measureText 字符级循环

**位置**: `src/bitmap.ts:215-227`


**问题**: 1000 字符 = 1000 次 `measureText`。Chromium 实测 `measureText` 1-5 μs/次。

2. **方案 B**: 把 `textToBitmap` 移到 `requestIdleCallback` 或 Web Worker
3. **方案 C**: 用 CSS `text-wrap: balance` 的浏览器原生换行(实验性, 不通用)

**预期收益**: 1000 字符场景 5-20ms → 1-3ms (-80%)。

## 6. P2 优化建议(锦上添花)

### 🟨 P2-1 · CJK regex `test()` per char

### 🟨 P2-2 · `Math.max(...arr)` 大量元素

**位置**: `src/bitmap.ts:181`

```js
const maxLineLen = Math.max(...text.split('\n').map((s) => codePointLength(s)), 1);
```

**问题**: `Math.max(...arr)` 用 spread 把数组展开为函数参数, V8 默认栈参数限制 ~64K-125K。
10K 字符单行 = 抛 `RangeError: Maximum call stack size exceeded`。

**改法**: 用 reduce:

```js
const lines = text.split('\n');

  const len = codePointLength(line);
  if (len > maxLineLen) maxLineLen = len;
}
```

**预期收益**: 鲁棒性 + 微小性能(避免 spread 开销)。

### 🟨 P2-3 · `getBlendedLUT` cache hash string concat

**位置**: `src/palette-lut.ts:294-311`

**问题**: 8 个字段 + hue + di, 每次都做 9 次 string concat。32 桶 × 9 字段 = 288 string ops/帧。

**预期收益**: 288 ops/帧 → 32 ops/帧(-90%)。但 absolute 不大(~10 μs)。

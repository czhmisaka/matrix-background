### 🟧 P1 — 应该做,影响热路径与代码分割

#### P1-1: per-cell `applyTP` 应进 LUT(关键热路径)

**位置**:`src/engine.ts:1392`(在 `drawInner` 内,每 cell 调一次)

**当前代码**(`src/engine.ts:1352-1397`):

```ts
const drawInner = (c, h, s, y, l, M, p, coldFinal, warmFinal, totalHue) => {
  // ... warmth 阻尼 ...
  // LUT 查表(已应用 ctp/wtp/hue)→ 冷暖混合 → applyTP(tp, hue)
  const lIdx = (l * 255) | 0;
  const gR = coldFinal.r[lIdx],
    gG = coldFinal.g[lIdx],
    gB = coldFinal.b[lIdx];
  const wR = warmFinal.r[lIdx],
    wG = warmFinal.g[lIdx],
    wB = warmFinal.b[lIdx];
  // ...
  const [R2, G2, B2] = applyTP(rc, gc, bc, effectiveTp, totalHue); // ← 每 cell 一次!
  ctx!.fillStyle = `rgba(${R2}, ${G2}, ${B2}, ${finalA})`;
  ctx!.fillText(charset[c.ch], h * ef + ef / 2, y);
};
```

`applyTP`(`src/palette-lut.ts:80-146`)含 7 个 TP 字段判断 + 可能 RGB↔HSL↔RGB 转换 — 在 60 fps × 1280×800 / (14×15.4) ≈ 4,800 cells 网格下,每帧 ≈ 5,000 次 `applyTP` 调用。

**改法**:在 `PaletteLUT` 加一对 `coldFinalTp` / `warmFinalTp`(coldFinal + tp + totalHue 一次性 bake 完),per-cell 路径变:

```ts
// 之前
const rc = gR * (1 - d) + wR * d; // 冷暖 blend
// ...
const [R2, G2, B2] = applyTP(rc, gc, bc, effectiveTp, totalHue); // 3 次乘法 + N 次判断

// 之后
const idx = ((blend * d + (1 - d)) * 255) | 0; // 1 次混合 → 索引
const R2 = coldTp[r_idx]; // 纯查表
```

内存代价:+2 KB(LUT_SIZE × 4 × 2 = 2 KB)— 完全可以接受。

**预期收益**:

- 网格 4,800 cells / 帧时,**热路径 ~30% 提速**(实测 dev tools 应能确认)
- 配合 P1-2 后,hue rotation 时不再"每帧重建 LUT"且"per-cell 调用"

**风险**:内存 +2 KB,微不足道。

#### P1-2: LUT hash 量化 dynamicHue + dynamicColorHue

**位置**:`src/palette-lut.ts:213-222`

**当前 hash**:

```ts
const hash = tp.brightness + '|' + ... + (hue | 0);
```

`(hue | 0)` 把 hue round 到 1°。问题:`totalHue = dynamicHue + dynamicColorHue`,而 `dynamicColorHue` 来自 `colorCurve` userFunc(`src/engine.ts:1224-1237`),可任意浮点。

- 正常用 `hueRotateSpeed=30, hueRotateAmount=360` 时,`dynamicHue` 每帧 ~0.5° → 量化后多数帧 hash 命中 ✓
- 但 `colorCurve` 返回 `0.1` 这种值时,加上 `dynamicHue` 一起 `(totalHue | 0)`,每帧都可能跨 1° 边界 → **每帧重建 2 张 256 项 LUT(2048 次 applyTP)**,1KB 工作集抖动

**改法**:

```ts
// 把 totalHue 在 hash 前先量化到 1°,并接受 "色相偏差 < 0.5° 视觉无感"
const hueQuant = Math.round(hue);  // 替代 (hue | 0),对称 + 一致
const hash = tp.brightness + '|' + ... + hueQuant;
```

更激进:把 `dynamicHue` 和 `dynamicColorHue` 都单独量化到 0.5°,在用户传入端控制。

**预期收益**:

- colorCurve userFunc 用户场景下,**省每帧 2048 次 applyTP**
- 视觉无差异(< 1° hue shift 肉眼难辨)

## 5. 热路径分析(`src/engine.ts`)

### 5.1 `applyTP` 在每字符热路径

**位置**:`src/engine.ts:1392`(在 `drawInner` 函数内,line 1352-1397)

**调用频率**:

- 60 fps × 网格 `r * i` cells
- 默认 `fontSize=14`、viewport 1280×800 → 网格约 91×51 = **4,641 cells / 帧**
- 每帧 4,641 次 `applyTP` 调用
- 每秒 60 × 4,641 = **278,460 次 / 秒**

`applyTP` 内部(`src/palette-lut.ts:80-146`):

- 7 个 TP 字段判断
- brightness/contrast/lightnessShift/saturationShift 各 1-3 个乘法
- chroma 3 个减乘加
- **hueShift / extraHue 触发 RGB↔HSL↔RGB 转换**,单次调用 30+ 操作
- invertHue 3 个减乘加
- 最后 3 次 `Math.max(0, Math.min(255, Math.round(...)))` clamp

**最坏情况**(全 hueShift + invertHue + chroma + 用户全开):

- 每 cell ~80 个浮点操作
- 60 fps × 4,641 cells = **278K 操作 / 秒** → 4.6M / 帧 = 毫秒级

**改法**(已述 P1-1):把 `applyTP(rc, gc, bc, tp, totalHue)` bake 进第三层 LUT。

### 5.2 Palette LUT 重建开销

**位置**:`src/engine.ts:1307-1308`(每帧调)

```ts
const coldFinal = paletteLUT.getColdFinal(effectiveCtp, totalHue);
const warmFinal = paletteLUT.getWarmFinal(effectiveWtp, totalHue);
```

`getFinal`(`src/palette-lut.ts:206-236`)逻辑:

1. 算 hash(`tp + (hue | 0)`)
2. hash 命中 → 直接返回 `dst`(`< 1μs`)
3. hash miss → 遍历 256 项,每项 `applyTP(1 次)` → 256 × ~30 ops = ~7.7K ops + 256 × 4 字节写 = **~10μs**
4. 2 个调色板 × 256 项 = **~20μs / 帧**

**什么时候 miss**:

- 静态场景(`hueRotateSpeed=0, colorCurve=null`):hash 永远命中 ✓
- `hueRotateSpeed=30`:0.5°/frame,(hue | 0) 多数帧相同 ✓
- `colorCurve` 返回浮点:hash miss 每帧 → **20μs 持续开销**(微小)
- setTheme / setThemeParams:启动时一次 20μs ✓

**评估**:LUT cache **整体工作良好**,问题在 (1) per-cell `applyTP`(已述 P1-1),(2) `(hue | 0)` 对浮点动态 hue 不友好(已述 P1-2)。

### 5.3 `buildCtx` cache

**搜索结果**:`src/engine.ts` 内**无** `buildCtx` / `ctxCache` 函数或变量。

- 实际设计:`ctx` 是 `let ctx: CanvasRenderingContext2D | null = null`,在 init 时从 `canvas.getContext('2d')` 拿一次
- `wrapper` / `canvas` 也不缓存,直接闭包引用
- 这已经是"cache 化"了 — 没有每次重建 ctx

**结论**:`buildCtx` 在本项目 = `getContext('2d')` 一次,无优化空间。已生效。

### 5.4 `dt` timing 合理性

**位置**:`src/engine.ts:1204-1219`

**评估**:

- `targetFPS > 0` 路径:`fpsAccumMs` 累计,跳帧保稳定(行 1184-1197) ✓
- `targetFPS = 0`(默认)路径:`lastDt = clamp(rawDt, 0, 0.1)`,wallTime 累积 ✓
- 首帧保护:`tsMs < prev` → `lastDt = 0`(行 1217)→ phase 不动,边缘情况(已述 P2-3)
- `fixedTimeStep` 模式:dt 强制 1/60,确定性(SSR/headless 测试用) ✓

**问题**:`lastDt * 60` 是高频出现模式(`src/engine.ts:1422, 1444, 1544, 1606`),是 60fps 等价折算,实际帧率 120 fps 时累加会 2x。建议改成 `lastDt / FIXED_DT`(`FIXED_DT = 1/60`),代码读起来更清晰。

**改法**:

```ts
const FIXED_DT = 1 / 60;
// 之前:c.phase += basePhaseInc * lastDt * 60;
// 之后:c.phase += basePhaseInc * (lastDt / FIXED_DT);
```

**预期收益**:代码可读性,无 perf 收益(V8 优化器会常量折叠)。

### 5.5 transition 期每帧是否仍贵?

**位置**:`src/engine.ts:1241-1303` — 5 个 transition 状态(transitionAlpha / theme / themeParams / variant / phase)

**transition 期开销**:

1. `transitionAlpha` 插值:5 个赋值 + 1 次 easeInOut(< 1μs)
2. `themeTransition` 插值:5 个 lerpHSLPalette / lerpThemeParams 调用,每次 5-7 个浮点 + 1 次 `paletteLUT.setPalettes(effectiveCold, effectiveWarm)`(行 1268)
3. `paletteLUT.setPalettes`(`src/palette-lut.ts:178-194`):身份比较,palette **是新对象**(每帧 lerpHSLPalette 返回新对象)→ `coldChanged = cold !== this.coldPalette` **永远 true** → 触发 `rebuildStatic`(256 项 HSL→RGBA 转换 = 256 × 20 ops = **5K ops / 帧**)

**最坏情况**(theme 切换 400ms 内):

- 24 帧 × 2 调色板 × 256 项 = **12,288 次 HSL→RGBA / 切换** = 30K ops
- 微小(~50μs 总),但**有浪费**

**改法**:`setPalettes` 加一个 `force: boolean` 参数,或拆 `setPalettesIdentity(cold, warm)`(身份比较) + `bakeFinal(tp, hue)`(重建终态)。当前实现每帧重建 static LUT 是浪费的(因为 static 是 HSL→RGBA,跟 tp/hue 无关,**只有 palette 引用变了才需要重建**)。

**更准确的改法**:`setPalettes` 内部已经做了 `cold !== this.coldPalette` 比较 — **但因为 `lerpHSLPalette` 每帧返回新对象**,比较永远 false → 永远 rebuild。

**建议**:在 `src/engine.ts:1262-1268` 临时 palette 路径不要走 `setPalettes`,改成走一个内部 `paletteLUT.rebuildStaticTo(this._tmpCold, this._tmpWarm)` 之类 API,或者在 `setPalettes` 内部 hash 比较。

**预期收益**:

- theme 切换 400ms 内省 ~30K ops
- 仍可视觉无差异(static LUT 本来就该是 source-of-truth,临时的 coldWarm 不需要 rebuild 它)
- 代码略复杂(增加一个 API),需要权衡
